## Decisions and operational contract

The operator explicitly selected:

- Check each new entry's available cash for its own margin and fees. Retain gross exposure caps; do not reserve three future breakout add-ons.
- Use the corrected selected isolated-liquidation model for hypothetical occupancy: funding debits reduce margin; receipts remain wallet cash. Rebuilding paper state must never create funded orders.

Approved continuation, structure, add-on, exit, direction-mode and same-open recovery restrictions were preserved. New size settings apply to future admissions; owned contract quantities and leverage come from actual execution history/venue state. MA operational size/leverage changes no longer invalidate otherwise compatible indicator/cooldown state. Changes to strategy rules still require compatible state and explicit review.

The funded runner now admits entries only with a candle/decision no more than 300 seconds old and a quote candle no more than 90 seconds old, measured at actual submission time. Deferred reversals retain their original intended open for the 300-second check. Missed bars still update causal state; expired entries do not become market orders. Exits bypass these admission gates, daily-loss limits and cash checks. These windows are operational safeguards, not optimized strategy parameters.

Portfolio notional is gross USD contracts across strategies. The margin cap values recorded BTC collateral and closing reserves at the current mark; new entries include an estimated reserve. The cash check uses `notional/leverage + notional*(0.002 + 0.001/leverage)`, conservatively allowing Tier-1 opening fees and the long-side liquidation closing reserve. It makes no promise of later add-on capacity; the venue remains authoritative at the actual fill. Fee/reserve semantics were checked against [LN Markets futures documentation](https://docs.lnmarkets.com/en/futures).

The daily-loss limit uses persisted net bot sats, including fees and funding, converted at the current mark. It is identical across event order and restart. This is a risk-control valuation, not historical USD P&L at each settlement price.

## Historical reconstruction evidence

[Historical rebuild artifact](btc-close-range-historical-rebuild-2026-09-27.json) verifies the original daily/seed hashes, all four unit fill identities/prices and every expected eight-hour settlement through the original September 12 completed-candle cutoff. It preserves campaign `20260822L`, four lifetime units, indicator history and source digest; every unit remains historical and unowned.

The hydrator uses a conservative monotone survival proof: final collateral after all funding debits gives the most adverse liquidation threshold. If every intervening candle survives that threshold, the units necessarily survived all earlier thresholds. A crossing does **not** prove the exact time/order of liquidation: reconstruction refuses certification and requires finer chronological evidence. It also rejects missing settlements, mismatched reference units and truncated candles. This limitation is deliberate and must not be bypassed by declaring a compact snapshot complete.

Historical price processing follows adverse threshold order and gap-at-open ties, matching the selected replay. If the parent liquidates first, surviving children close hypothetically at that price instead of a later child threshold. Every such event remains unowned.

Live continuation checks funding coverage before hypothetical price processing. A funding gap invalidates model completeness and persists the block; a later favorable quote cannot certify prices skipped during the gap. Rebuilding on restart requires complete evidence. Funded exits continue. The model is an isolated-liquidation approximation, not a venue order-book/liquidation guarantee.

[Corrected fixed-model result](btc-close-range-corrected-fixed-model-2026-09-27.json) records one continuous `structure_parent_addons_raw` scenario, 2020-01-01 through 2026-09-13, with frozen $1,000 research units. It records 49 parents, 140 units and 18 unit liquidations. Input/source hashes and limitations accompany the result. Full units/parents/funding/equity traces are in `/tmp/lnmbot-remediation-20260926/selected-model-corrected/`. No parameter search or selection was performed. This replay does not validate funded wallet affordability or forecast future returns.

## Read-only preflight and deployment procedure

Obtain a consistent SQLite backup using an operator-authorized SQLite backup transaction. Copying only the main database file while WAL is active is insufficient. Keep account evidence/DB copies outside Git and do not copy credentials into this workspace.

Run the candidate against an isolated DB copy and inspect it without migrations or writes:

```sh
PYTHONPATH=src .venv/bin/python scripts/check_remediation_readiness.py --db /tmp/lnmbot-preflight.sqlite
```

The checker reports integrity, required tables, missing fills/P&L, duplicate trade actions, funding-attribution mismatches, daily-event total differences, unresolved commands, undelivered external events and historical evidence blocks. Stable instance snapshots take precedence over retained legacy class snapshots, matching the runtime readers. `local_consistency_pass` is only local evidence; `deployment_approved` is always false. It makes no venue request and changes no database. Run additive schema initialization and restore tests separately **only on the copy**, then repeat the scan. Do not interpret a new empty schema as repaired trading history.

Before switching:

- Record independent running/open/closed venue inventories and funding history, all pages, against immutable recorded ownership. Include funding for closed trades. Compare per-strategy and daily sats with venue-derived results.
- For incomplete old actions, prepare a repair transaction with exact venue IDs, fills, fees, timestamps and changed aggregates. Review its dry-run diff and provenance. Never estimate a historical execution price to make totals balance. This remediation did not perform that repair.
- A `submitted` entry is unresolved, not evidence of rejection. A single empty running-trade response is insufficient: the request may appear later or already be closed. Review the archived request/decision state and complete account history. Apply accepted/rejected disposition only with definitive evidence and explicit strategy-state treatment; retain the command identity. There is no automatic ownership-matching/adoption utility in this change. Unknown trades must not be silently assigned or closed.
- `received` means an authoritative result awaits atomic application; startup replays it before restoring ownership. `applied` means local facts committed. External events remain undelivered until their strategy snapshot and acknowledgement commit together. Existing closing slots and pending reversal state must be reviewed alongside command status.
- Build a new, empty immutable release from a reviewed clean commit/allowlist. Include the new `strategy/historical.py`, command schema/recorder, runner and verified seed/reference artifacts required by the configured paths. Do not export the entire dirty checkout or use the dated rebuild artifact as current state. Trader and dashboard have separate release switches.
- Plan rollback of **code** with forward-compatible state/accounting. Old code ignores the command ledger and new hypothetical fields and must not be resumed blindly after new funded actions. Never restore an old DB over new trading records. Keep the candidate or a compatible recovery release until a reviewed rollback is safe.
- Obtain approval for the exact service switch/migration transaction only after copy-based restore, accounting and venue checks pass. Verify ownership, pending exits, entry gates, funding, risk totals and dashboard after switching. Do not use a whole-engine halt as an entry-only pause: it also suspends owned-position management.
